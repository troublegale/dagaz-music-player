# Dagaz Music Player Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Выпустить личный self-hosted плеер с сервером Ubuntu, клиентами Windows/Android, редактированием файлов, офлайном и переносом воспроизведения.

**Architecture:** Один сервер Rust/Axum с SQLite и внутренними заданиями, RustFS для объектов, Caddy для HTTPS. Windows — Rust/GPUI Kit; Android — Kotlin/Compose/Media3. Общими являются протокол и сценарии поведения; платформенные воспроизведение и кеш остаются отдельными.

**Tech Stack:** Rust, Axum, Tokio, SQLx/SQLite/FTS5, RustFS/S3, Lofty, FFmpeg, GPUI Kit, Rodio/Symphonia (после проверки), Kotlin, Compose, Room, Media3, Docker Compose, Caddy.

**Spec:** [Согласованное проектирование](../specs/2026-11-18-dagaz-music-player-design.md).

## Global Constraints

- Один сервер обслуживает одну личную библиотеку; клиент настраивает подключение к серверу.
- Поддерживаются WAV, MP3, FLAC. Пользователь не задаёт ограничение на количество треков.
- Правки метаданных записываются в аудиофайлы на сервере.
- Три качества: оригинал, высокое, низкое. Выбор отдельно для стриминга и скачивания.
- Загрузка на сервер, изменение тегов и плейлистов требуют подключения.
- Windows 10/11 x64; Android 9+ arm64 как начальные целевые платформы.
- Одно активное устройство на связи; офлайн-воспроизведение разрешено. Старое устройство после переподключения уступает более новому владельцу.
- До выполнения плана создаются только документы. Этот план не является разрешением самостоятельно начать реализацию.

## Review Focus

1. Повтор запроса после потери ответа не создаёт второй трек, задание или перенос: тесты S2, S6, S7.
2. Смена ревизии во время докачки не смешивает старые и новые байты: тесты S3, W3, A3.
3. Переименование/удаление на другом клиенте сохраняет поиск и завершённый офлайн-файл: S4, W3, A3.
4. Запоздавший прогресс старого устройства не возвращает ему воспроизведение: S7, W4, A4, R1.
5. Кириллица, кавычки, одноимённые альбомы и нехватка диска дают корректный результат или явную ошибку: S2–S5, W5, A5.

## Единый контракт для всех планов

P1 создаёт Rust-типы и OpenAPI; остальные задачи реализуют перечисленные операции. Поля JSON — `snake_case`, идентификаторы — UUID-строки, даты — UTC RFC3339, позиции/длительности — целые миллисекунды. Ревизии, последовательности и эпохи — положительные `i64`/Kotlin `Long`; первый номер — 1. Страница по умолчанию 100 записей, максимум 500; курсор привязан к фильтру и порядку.

Основные DTO:

- `Quality = original | high | low`.
- `ApiError { code, message, request_id, job_id? }`; HTTP 401/403 — доступ, 404 — отсутствие, 409 — конфликт ревизии/эпохи/смещения, 410 — устаревший курсор или удалённая ревизия, 413 — размер, 415/422 — формат/содержимое, 425 — представление готовится, 507 — место закончилось. Ошибки 5xx и сетевые сбои повторяются только с защитой от повторного выполнения.
- `Track { id, revision, filename, title, artist, artist_id, album_id, album, album_artist, track_number, disc_number, duration_ms, format, artwork_id, original_bytes, ready_qualities }`; nullable-поля явно отмечаются в OpenAPI. Альбом/обложка могут отсутствовать; `artist`/`title` допускают отсутствие тегов и получают подпись для отображения на клиенте.
- `MetadataPatch { title?, artist?, album?, album_artist?, track_number?, disc_number?, artwork_id? }`. Отсутствующее поле сохраняется; `null` очищает допустимое поле; непустое значение устанавливает. Rust должен сохранять различие missing/null/value, а не сводить его к обычному `Option<T>`.
- `Playlist { id, revision, name, track_ids, next_cursor, total_count }`; track_ids содержит текущую страницу, при записи передаётся полный порядок. Порядок массива значим, повтор трека разрешён. Страницы привязаны к ревизии плейлиста; её смена требует перечитать состав. Замена состава проверяет ожидаемую ревизию.
- `MediaDescriptor { track_id, revision, requested_quality, effective_quality, byte_length, sha256, etag, url }`; URL относится к неизменной ревизии. `Original` может удовлетворять `High/Low`, когда повторное сжатие MP3 не требуется.
- `UploadState { id, offset, total_bytes, expires_at, status }`, status = uploading | processing | completed | failed | expired; `Job { id, kind, status, result, errors }`; состояния задания: `queued | running | succeeded | partial | failed`.
- `Change { sequence, entity, entity_id, revision, deleted, payload }`; `SyncPage { generation, changes, next_cursor, has_more }`.
- `PlaybackState { epoch, owner_device_id, track_id, queue, play_order, queue_index, position_ms, paused, repeat, shuffle_seed, last_report_sequence }`. queue — исходные треки с возможными повторами; play_order — материализованная перестановка индексов очереди, queue_index — текущее вхождение в queue. Все клиенты следуют play_order и не строят новую перестановку из seed при переносе. repeat = off | one | all; отсутствующий shuffle_seed выключает перемешивание и даёт естественный play_order. Сервер проверяет, что play_order — точная перестановка индексов без потерь/повторов.
- `PlaybackCommand { operation_id, expected_epoch, action, payload }`; действия: `play_here | pause | resume | seek | next | previous | replace_queue | set_modes | transfer`. `PlaybackReport { epoch, sequence, track_id, queue_index, position_ms, paused }` принимается только от владельца и с возрастающим `sequence`.
- `PlaybackAck { operation_id, epoch, phase, position_ms?, error? }`; `phase = ready | stopped | started | failed`. Payload команд фиксируется в OpenAPI: pause/resume/next/previous — пустой; seek — position_ms; transfer — target_device_id; play_here/replace_queue — queue, play_order, queue_index, position_ms, repeat, shuffle_seed; set_modes — repeat, shuffle_seed, play_order. Локальная громкость не входит в серверное состояние.

| Метод и путь `/api/v1` | Вход → выход / назначение |
| --- | --- |
| `POST /pair` | `{ pairing_code, device_name, platform }` → `{ device_id, token }`; одноразовый код, без токена устройства |
| `GET /devices`, `DELETE /devices/{id}` | Список/отзыв устройств; все дальнейшие операции требуют Bearer token |
| `GET /tracks`, `/albums`, `/artists` | `q`, `sort`, `cursor`, `limit` → страница сущностей |
| `GET /albums/{id}/tracks` | Страница треков альбома в порядке disc/track |
| `GET /tracks/{id}` | `Track` |
| `POST /uploads` | `{ filename, total_bytes, sha256 }` + `Idempotency-Key` → `UploadState` |
| `GET /uploads/{id}` | Состояние для продолжения |
| `PATCH /uploads/{id}` | Binary + `Upload-Offset` + `X-Chunk-SHA256` → новое смещение; часть до 8 МиБ |
| `POST /uploads/{id}/complete` | `Idempotency-Key` → `Job`; итог содержит существующий или новый `track_id` |
| `GET /jobs/{id}` | Статус и результаты обработки |
| `POST /artworks`, `GET /artworks/{id}` | JPEG/PNG → ID; чтение/миниатюра |
| `PATCH /tracks/{id}/metadata` | `{ expected_revision, patch }` + `Idempotency-Key` → `Job` |
| `POST /tracks/metadata-batch` | `{ items: [{ track_id, expected_revision }], patch }` → `Job` с результатом каждого файла |
| `DELETE /tracks/{id}` | Ожидаемая ревизия → tombstone; объект удаляется отложенно |
| `GET /playlists`, `POST /playlists` | Список; `{ name }` → `Playlist` |
| `GET /playlists/{id}`, `PATCH /playlists/{id}`, `DELETE /playlists/{id}` | Чтение; переименование/удаление с ожидаемой ревизией |
| `PUT /playlists/{id}/tracks` | `{ expected_revision, track_ids }` → новая ревизия; порядок и повторы сохраняются |
| `GET /tracks/{id}/media`, `HEAD /tracks/{id}/media` | `revision`, `quality`; Range/If-Range/ETag, стабильные байты |
| `POST /download-manifests` | `{ kind: track|album|playlist, id, quality }` → ID снимка состава |
| `GET /download-manifests/{id}` | Страница `{ items: MediaDescriptor[], next_cursor, selection_revision }`; снимок неизменен, создание повторяемо по ключу операции |
| `GET /snapshot`, `GET /changes` | Начальный каталог/дельта; см. S4 |
| `GET /playback`, `POST /playback/commands` | Состояние; команда с защитой от повторов → принятое состояние/операция |
| `POST /playback/reports`, `POST /playback/acks` | Фактический прогресс/подтверждение фазы; автор устройства берётся из токена |
| `GET /events` | WebSocket: `catalog_changed`, `job_changed`, `playback_state`, `prepare`, `stop`, `start`, `device_revoked`; после reconnect клиент читает состояние/дельту |

`GET /healthz` находится вне `/api/v1`, не требует токена и не раскрывает секретов. При готовящемся качестве ответ 425 содержит `job_id`; клиент ждёт событие/статус, без скрытого переключения на другой профиль. Все изменяющие операции, которые клиент может повторить после потери ответа, получают `Idempotency-Key`; команды воспроизведения используют `operation_id`.

Для shuffle и офлайн-очереди replace_queue передаёт queue/play_order/queue_index/режимы/позицию. При той же epoch и владельце клиент после reconnect может согласовать своё локальное состояние, затем отправлять reports; при изменившейся epoch сначала принимает серверное решение. Каждая принятая управляющая команда увеличивает epoch, поэтому запоздавший heartbeat не отменит более свежую паузу или очередь даже при том же владельце. Reports сами epoch не меняют.

Окончательная схема OpenAPI и примеры фиксируются в P1 до параллельного развития клиентов. Любое её изменение обновляет Rust DTO, Kotlin-модели, примеры и тесты трёх сторон в одной задаче.

## Общие правила проверки и ресурсы

- Rust: `cargo fmt --all -- --check`. На Ubuntu: `cargo clippy -p dagaz-protocol -p dagaz-server --all-targets -- -D warnings`, `cargo test -p dagaz-protocol -p dagaz-server`. На Windows: те же команды для `-p dagaz-protocol -p dagaz-windows`. Полный workspace не объявляется переносимым на любую ОС; GPUI проверяется на Windows.
- Android из `apps/android`: `./gradlew testDebugUnitTest lintDebug assembleDebug`; на Windows — `gradlew.bat`; реальное устройство: `./gradlew connectedDebugAndroidTest`.
- Интеграция с RustFS: `docker compose -f deploy/compose.test.yaml up -d --wait`, затем тесты с выделенным endpoint и учётными данными. Использовать только отдельный тестовый том; не запускать `down -v` для рабочего Compose.
- Для проверок сети используются ограничение скорости и отключение сети на тестовом устройстве; имитация транспорта покрывает детерминированные сбои. Реальные устройства обязательны в R1–R2.
- Фикстуры — короткие сгенерированные сигналы/свободные образцы, кириллица, обложка, отсутствующие теги, повреждение, VBR MP3, PCM/float WAV и FLAC. Библиотеку пользователя не использовать как единственный тест и не менять оригиналы во время проверок.
- Каждая проверка записывает версию зависимостей, команду, устройство и результат. Сейчас результатов сборок и измерений нет.

## Готовность, зависимости и оценка

Критический путь: P1 → P4/P5 → P2/P3 → P6 → S1–S4 → два клиента воспроизводят → S5 + W5/A5 → S6 + W3/A3 → S7 + W4/A4 → R1–R4. Работы над платформами можно выполнять независимо после фиксации протокола, но этот план сам по себе не включает параллельный запуск агентов.

Оценку по календарю даём после P1–P6 и первой работающей связки: сейчас нет измерений сборки GPUI, сложности сетевого источника Rodio, характеристик VPS и устройства Android. До R1 потребуются реальный телефон, Windows-компьютер и тестовый VPS; до R3 — доменное имя и место для резервной копии вне VPS. Эти доступы не нужны для написания плана и большей части локальной разработки.

Не выполнены до начала реализации: все P/S/W/A/R задачи, макеты, сборки, тесты и развёртывание. Пользователь согласовал проектирование; последующее начало разработки — отдельный шаг после чтения плана.
