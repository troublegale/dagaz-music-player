# Dagaz Integration and Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Проверить два настоящих клиента вместе и подготовить воспроизводимую установку, восстановление и личный выпуск.

**Architecture:** Уже реализованные сервер и клиенты проходят совместную приёмку. Сервер поставляется контейнером с Compose/Caddy, Windows — готовым portable-пакетом, Android — подписанным APK; публикация во внешние магазины не требуется.

**Tech Stack:** Существующий стек проекта, Docker Compose, Caddy, Cargo release, Gradle release, штатные инструменты ОС для измерений и SSH-копирования.

**Spec:** [Проектирование](../specs/2026-11-18-dagaz-music-player-design.md), [общий маршрут и контракт](2026-11-18-dagaz-music-player-plan.md).

## Global Constraints

- Одно устройство на связи; офлайн-воспроизведение разрешено и уступает новому владельцу при переподключении.
- Локальный поиск p95 до 100 мс, серверный поиск p95 до 200 мс без сетевой задержки.
- Старт готового сетевого представления до 2 секунд при RTT до 100 мс и доступных 10 Мбит/с, локальный старт до 500 мс.
- Контрольный набор — 100 тысяч записей каталога; для 60 Гц проверяется бюджет кадра 16,7 мс.
- Резервная копия хранится отдельно от VPS; восстановление проверяется на чистой установке. Все ограничения общего плана применяются.

## Review Focus

- Все изолированные тесты проходят, но клиенты по-разному понимают очередь/повтор трека: R1.
- На слабом телефоне/большом каталоге операции блокируют интерфейс: R2.
- Снимок БД и S3 не согласованы или backup остался только на VPS: R3.
- Обновили image, но миграция исключает простой откат: R3.
- Локальная сборка работает, а пакет без dev-инструментов/с потерянным APK-ключом не обновляется: R4.

## R1. Совместная приёмка Windows ↔ Android и метро

**Depends:** S1–S8, W1–W5, A1–A5.
**Files:** Create `docs/acceptance.md`, `docs/validation/cross-device.md`; при обнаружении ошибки правится ответственный модуль с регрессионным тестом в его существующем suite, а не отдельный слой обходов.
**Interfaces:** Uses только публичный API P1 и настоящие UI/медиа-сервисы. Produces заполненную матрицу приёмки с версиями/устройствами, редактированными логами состояния и найденными дефектами. Идентификаторы/epoch/позиция позволяют сопоставить события без логирования токенов.

- [ ] Подготовить две независимые привязки к одному тестовому серверу, короткие и длинные файлы всех форматов, плейлист с повторяющимся треком и скачанный набор. Матрица сначала имеет статус «не проверено», а не PASS по компиляции.
- [ ] Пройти в обе стороны: воспроизведение → перенос → пауза/seek/очередь/режимы; подготовить target медленно/без сети; потерять source до stop-ack; повторить команду после потери ответа. Проверить фактическую остановку звука и позицию, а не только серверный owner_id.

```text
online_playing_devices == 1
handoff_position_error_ms <= 500
same_operation_actual_starts == 1
queue_occurrence_and_play_order_before == queue_occurrence_and_play_order_after
```

- [ ] Пройти «метро»: телефон играет скачанное → отключить сеть → компьютер начинает → вернуть сеть телефона. Проверить остановку телефона до отправки старого состояния. Отдельно: простая потеря сети без смены владельца, пользовательская пауза, исчерпание буфера, перезапуск приложения, неполная загрузка, истёкший manifest/cursor и удаление трека/плейлиста с другого клиента.
- [ ] Проверить загрузку и пакетную правку с обоих устройств одновременно, частичный успех, одинаковые имена, совпавшие байты, свежесть поиска/обложек и сохранность локальных копий. Проверить само воспроизведение трёх качеств и правильное фактическое качество офлайн.
- [ ] На каждый дефект добавить минимальный падающий тест в S/W/A-задачу, исправить корень и повторить только затронутые сценарии плюс соответствующий suite. В `docs/acceptance.md` отметить реальные PASS/FAIL, версии и ограничения; R1 готов, когда обязательные сценарии не имеют открытых FAIL.
- [ ] Контрольная точка: `git add docs/acceptance.md docs/validation/cross-device.md` и изменённые файлы исправлений; `git commit -m "test: verify cross-device and offline journeys"`.

## R2. Проверка удобства и измерение быстродействия

**Depends:** R1; отдельные измерения можно начинать после S4/W2/A2.
**Files:** Create `apps/server/tests/performance.rs`, `apps/windows/tests/performance.rs`, `apps/android/app/src/androidTest/java/io/dagaz/player/PerformanceTest.kt`, `docs/validation/performance.md`; Modify `docs/ui/layout.md` и только подтверждённые узкие места продукта.
**Interfaces:** Produces воспроизводимые результаты с аппаратурой, warm/cold режимом, количеством записей, сетевыми условиями и p95. Генератор 100 тысяч записей работает только с временной тестовой БД, без наполнения пользовательской библиотеки.

- [ ] Написать измерительные тесты `large_catalog_search_p95` для сервера/Windows и `PerformanceTest.localSearchAndPlaybackStart` для Android: набор запросов с кириллицей/частичным словом/пустой выдачей, поиск p95, локальный старт, готовый сетевой старт. Длинные тесты пометить opt-in/ignored, чтобы обычный suite не зависел от нестабильных таймингов.

```rust
assert!(local_search_p95_ms <= 100);
assert!(server_search_p95_ms <= 200);
assert!(local_audio_start_ms <= 500);
assert!(ready_network_audio_start_ms <= 2000);
```

- [ ] Выполнить `cargo test -p dagaz-server --test performance -- --ignored --nocapture`, Windows аналогично, Android PerformanceTest на физическом устройстве. Для сети зафиксировать RTT/скорость до измерения; cold transcode не включать в «готовое представление». Проверять первый реальный аудиовывод, а не начало HTTP-запроса.
- [ ] Проверить release-интерфейсы: длинные списки, быстрая прокрутка, обложки, активная загрузка/редактор, масштабирование Windows и крупный шрифт Android. Замерить кадры штатным профилировщиком, сохранить p95 и долю кадров выше 16,7 мс, проверить отсутствие длинных блокировок. Проверить клавиатуру/фокус и TalkBack, имена кнопок, контраст и видимость сети/скачиваний.
- [ ] Исправлять только измеренные проблемы: блокирующий вызов, отсутствие индекса, повторная загрузка обложек, ненужный полный рендер. Если цель не достигнута, записать фактическое значение и причину и продолжить исправление до приёмки; не менять целевые цифры молча. Повторить затронутый тест и сценарий, не добавлять speculative-кеши.
- [ ] Контрольная точка: `git add apps/server/tests/performance.rs apps/windows/tests/performance.rs apps/android/app/src/androidTest/java/io/dagaz/player/PerformanceTest.kt docs/validation/performance.md docs/ui/layout.md` и узкие исправления; `git commit -m "perf: meet measured library and playback targets"`.

## R3. Чистая установка, backup/restore и обновление

**Depends:** S8, R1.
**Files:** Create `deploy/{Dockerfile,compose.yaml,Caddyfile,.env.example}`, `scripts/install.sh`, `docs/installation.md`; Modify `docs/backup.md`, `docs/development.md`.
**Interfaces:** Produces установочный bundle для архитектуры VPS, проверенной P6. `install.sh --domain <name> --data-dir <absolute-path>` выполняет preflight, генерирует случайные секреты, создаёт конфигурацию с закрытыми правами, запускает Compose и выводит адрес/первый код привязки. Повторный запуск с существующими данными отказывает в переинициализации; отдельное обновление сохраняет состояние. Источник bundle и checksum задокументированы, образы фиксируются по проверенной версии/digest.

- [ ] Сначала проверить на временных каталогах preflight/повторный запуск установщика через `bash -n scripts/install.sh` и небольшой `scripts/tests/install.sh`: занятые порты, отсутствующий Docker/Compose, несовпавшая архитектура, неготовый DNS, существующий data-dir, прерванный запуск. Проверка DNS не печатает секретов. Установщик предлагает конкретную команду установки отсутствующего Docker, а не выполняет неизвестные сторонние команды молча.

```text
reinstall_existing_data => refused_without_changes
rustfs_ports_visible_from_outside => false
secrets_file_permissions => owner_only
failed_preflight => no_reinitialization
```

- [ ] Подготовить multi-stage image приложения с FFmpeg и минимальным runtime, три сервиса Compose: app, rustfs, caddy. SQLite/staging/объекты/Caddy state — постоянные тома. S3/console не публиковать наружу. Локальный image/bundle можно установить без публикации в registry; источник и архитектура образа фиксируются при сборке. Запуск от непривилегированного пользователя, shutdown/healthcheck и пределы ресурсов определяются P6. Выполнить `docker compose -f deploy/compose.yaml --env-file <test-env> config --quiet`: PASS, конфигурация валидна.
- [ ] На чистой тестовой Ubuntu выполнить установку по инструкции с реальным доменом/HTTPS. Подключить оба клиента, загрузить/отредактировать/скачать музыку. Перезапустить контейнеры и VPS, убедиться в сохранности данных. Проверить снаружи закрытость RustFS и работу только приложения.
- [ ] Через CLI S8 получить согласованный backup в закрытый каталог, безопасно перенести по SSH на отдельный компьютер/носитель и проверить checksum; содержащие секреты копии хранить в зашифрованном хранилище. Остановить тестовую установку и восстановить на другом чистом экземпляре, проверить теги оригиналов, обложки, плейлисты, новые курcоры, доступ клиентов и повторную генерацию качеств. Незавершённые операции не восстанавливают случайное воспроизведение.
- [ ] Отрепетировать обновление с миграцией и отказ после миграции. Откат выполняется проверенной парой прежний image + совместимый снимок БД/объектов; рабочие тома не удаляются. В `docs/installation.md` и `docs/backup.md` записать точные команды и проверенную версию Ubuntu, обязательные DNS/порты, внешнее место копии и фактический результат восстановления.
- [ ] Контрольная точка: `git add deploy scripts/install.sh scripts/tests/install.sh docs/installation.md docs/backup.md docs/development.md`; `git commit -m "build: package self-hosted install and recovery"`.

## R4. Воспроизводимые клиентские сборки и первая версия

**Depends:** R1–R3 и все задачи клиентов.
**Files:** Create `packaging/windows/README.md`, `docs/releases/0.1.0.md`, `.github/workflows/check.yml`, `.github/workflows/build.yml`; Modify `apps/windows/Cargo.toml`, `apps/android/app/build.gradle.kts`, `docs/installation.md`.
**Interfaces:** Produces `dagaz-windows-0.1.0-x64.zip`, `dagaz-android-0.1.0-arm64.apk`, server image/bundle, SHA-256 manifest и инструкцию установки. CI-файлы описывают проверки/сборки, публикация и отправка во внешний сервис остаются ручным явно запрошенным действием. Локальные команды сборки работают независимо от GitHub.

- [ ] Выполнить итоговые проверки: Rust fmt/clippy/tests на Ubuntu для protocol/server и на Windows для protocol/windows; отдельный RustFS для integration. Android `./gradlew testDebugUnitTest lintDebug assembleDebug connectedDebugAndroidTest`; результаты PASS. Игнорируемые performance-тесты уже выполнены в R2 и не объявляются проверенными по обычному suite.
- [ ] Настроить проверки в CI, повторяя эти же команды: Ubuntu, Windows, Android unit/lint/build; реальные device-тесты — отдельный ручной шаг выпуска с записью результата, не мнимый PASS эмулятора. Зафиксировать lockfiles, Gradle wrapper, toolchains, версии и API v1. Не включать локальные секреты/установочные env/ключи в artifacts.
- [ ] Собрать Windows `cargo build --release -p dagaz-windows` и portable zip с нужными runtime-файлами/лицензиями. На чистом Windows-профиле без Rust/C++ build tools проверить запуск, подключение, звук, папки, офлайн и повторный запуск. Инструкция объясняет распаковку/первый запуск; MSI/магазин/платный сертификат не являются условием личного выпуска.
- [ ] Создать отдельный release signing key Android вне Git, сохранить защищённую резервную копию; передавать signing data через локальное/CI secret-хранилище без вывода паролей. Выполнить `./gradlew assembleRelease`, установить APK на телефон и проверить обновление предыдущей сборки с тем же ключом: настройки, привязка и скачанное сохраняются. Если предыдущей версии ещё нет, провести обновление между двумя тестовыми build version codes.
- [ ] Сформировать checksums, версию API и release notes с реальными проверками и известными ограничениями, проверить отсутствие прототипов/секретов в пакетах. Убедиться, что каждый сценарий раздела 14 проектирования имеет PASS или явно согласованное изменение требований; неподтверждённые обязательные сценарии блокируют выпуск.
- [ ] Контрольная точка: `git add packaging docs/releases/0.1.0.md .github apps/windows/Cargo.toml apps/android/app/build.gradle.kts docs/installation.md`; `git commit -m "release: prepare Dagaz personal player 0.1.0"`. Пакеты сначала доступны локально; загрузка в магазины/хостинг не выполняется автоматически.
